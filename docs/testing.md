## 2. Detailed Test Cases & Raw Outputs

### Test A: Service Readiness and Reboot Persistence

#### Objective
Validate that all network interface initializers, AP services, DHCP/DNS daemons, packet filtering rules, and kernel forwarding settings persist across a hard host reboot.

#### Verification Commands Executed on Pi
```bash
# Check service states
systemctl is-active ina-ap-interface hostapd dnsmasq nftables

# Verify persistent kernel forwarding
sysctl net.ipv4.ip_forward
```

#### Observed Output
```text
active
active
active
active
net.ipv4.ip_forward = 1
```

#### Outcome & Interpretation
After rebooting the Raspberry Pi 5 (`sudo reboot`), all four system units automatically initialized in their designated dependency order without human intervention. The SSID `INA-Router` reappeared in client Wi-Fi scans, client devices associated successfully, DHCP addresses were issued, and internet traversal resumed immediately.

### Test B: DHCP Allocation & Device Discovery Telemetry

#### Objective
Confirm client IP lease assignment via `dnsmasq` and active link-layer neighbor tracking in the kernel ARP cache.

#### Verification Commands Executed on Pi
```bash
# Inspect ARP / neighbor table on virtual AP interface
ip neigh show dev ap0

# Inspect active DHCP leases
sudo cat /var/lib/misc/dnsmasq.leases
```

#### Observed Raw Output
```text
192.168.50.46 lladdr 5e:22:f6:20:9a:e7 REACHABLE
1793087276 5e:22:f6:20:9a:e7 192.168.50.46 * 01:5e:22:f6:20:9a:e7
```

#### Detailed Field Analysis
1. **Neighbor Table:**
   - IP `192.168.50.46` maps to MAC `5e:22:f6:20:9a:e7` with state `REACHABLE`, confirming bidirectional link-layer communication over the `ap0` Wi-Fi link.
2. **DHCP Lease Record:**
   - **`1793087276`:** Unix epoch timestamp indicating **when the lease expires** (calculated as `assignment_time + 12h`). This is an expiration timestamp, not the time of test execution.
   - **`5e:22:f6:20:9a:e7`:** The client link-layer address. The second least-significant bit of the first byte (`0x5e = 01011110b`, bit 1 is set) indicates a randomized, locally administered MAC generated by the client OS.
   - **`192.168.50.46`:** Assigned dynamic IP within the configured pool (`192.168.50.10`–`192.168.50.100`).
   - **`*`:** Unassigned hostname. Denotes that the client operating system did not transmit DHCP Option 12 (Host Name).
   - **`01:5e:22:f6:20:9a:e7`:** DHCP Client Identifier (Option 61), composed of hardware type `01` (Ethernet/Wi-Fi) followed by the hardware MAC.

### Test C: Local Link Latency & Packet Loss Benchmark

#### Objective
Evaluate packet loss and round-trip latency on the local wireless segment between the Fedora client workstation and the Raspberry Pi 5 gateway.

#### Test Command Executed on Client Workstation
```bash
ping -c 20 192.168.50.1
```

#### Observed Summary Statistics
```text
20 packets transmitted, 20 received, 0% packet loss, time 19028ms
rtt min/avg/max/mdev = 0.718/34.672/142.627/38.457 ms
```

#### Statistical Breakdown
- **Packets Transmitted:** 20
- **Packets Received:** 20
- **Packet Loss:** **0.0%**
- **Minimum RTT:** 0.718 ms
- **Average RTT:** 34.672 ms
- **Maximum RTT:** 142.627 ms
- **Standard Deviation (`mdev`):** 38.457 ms

#### Technical Interpretation
Zero packet loss confirmed high link reliability over the local 802.11 association. However, latency varied substantially: while minimum latency was sub-millisecond (0.718 ms), latency spikes reached 142.627 ms, yielding a standard deviation of 38.457 ms. This jitter is typical for a virtual AP interface (`ap0`) sharing a physical wireless radio with an active Wi-Fi station link (`wlan0`). **The local Wi-Fi link must not be claimed to have consistently low latency.**

### Test D: External Path Latency & Packet Loss Benchmark

#### Objective
Evaluate end-to-end traversal latency and packet loss from the local client across the Pi router and mobile phone hotspot to the public internet.

#### Test Command Executed on Client Workstation
```bash
ping -c 20 8.8.8.8
```

#### Observed Summary Statistics
```text
20 packets transmitted, 17 received, 15% packet loss, time 19026ms
rtt min/avg/max/mdev = 142.357/210.680/269.136/36.377 ms
```

#### Statistical Breakdown
- **Packets Transmitted:** 20
- **Packets Received:** 17
- **Packet Loss:** **15.0%**
- **Minimum RTT:** 142.357 ms
- **Average RTT:** 210.680 ms
- **Maximum RTT:** 269.136 ms
- **Standard Deviation (`mdev`):** 36.377 ms

#### Technical Interpretation
The external path exhibited high latency (averaging 210.680 ms) and 15% packet loss (3 packets dropped out of 20). The tested network path encompasses multiple hops:
`Client -> [Local Wi-Fi] -> Pi ap0 -> Pi wlan0 -> [Uplink Wi-Fi] -> Phone Hotspot -> [Cellular Radio Access Network] -> Internet`.

Because packet loss was 0% on the local hop (Test C), the 15% loss and high latency are attributable to upstream hops (the phone hotspot, mobile cellular network conditions, or double Wi-Fi hop contention). The root cause was not isolated during this session. **Do not attribute the packet loss conclusively to either the Raspberry Pi router or the mobile uplink.**

### Test E: Local TCP Throughput Benchmark (`iperf3`)

#### Objective
Measure local TCP data transfer rates and retransmission counts over the local Wi-Fi link.

#### Test Setup
1. **Server:** Raspberry Pi 5 (`192.168.50.1`), running `iperf3 -s` bound to default TCP port 5201.
2. **Client:** Fedora Laptop (`192.168.50.46`), running `iperf3 -c 192.168.50.1 -t 20`.

#### Test Command Executed on Client Workstation
```bash
iperf3 -c 192.168.50.1 -t 20
```

#### Observed Raw Output
```text
Connecting to host 192.168.50.1, port 5201
[  4] local 192.168.50.46 port 43812 connected to 192.168.50.1 port 5201
[ ID] Interval           Transfer     Bitrate         Retr
[  4]   0.00-20.00 sec  63.4 MBytes  26.6 Mbits/sec   32             sender
[  4]   0.00-20.02 sec  60.1 MBytes  25.2 Mbits/sec                  receiver
```

#### Metric Breakdown
- **Test Duration:** 20.00 seconds
- **Data Transferred (Sender):** 63.4 MBytes
- **Throughput (Sender):** 26.6 Mbits/sec
- **Data Transferred (Receiver):** 60.1 MBytes
- **Throughput (Receiver):** 25.2 Mbits/sec
- **TCP Retransmissions:** 32 retransmits

#### Technical Interpretation
The test achieved an average sustained TCP receiver throughput of **25.2 Mbps** over the local Wi-Fi connection. Periodic throughput fluctuations were observed during the run, including one 1-second interval where zero bytes were transferred, followed by a burst of retransmissions. This behavior is consistent with single-radio channel contention between the virtual AP (`ap0`) and background beaconing/activity on the physical interface (`wlan0`).

This 25.2 Mbps measurement serves as a factual performance baseline for this physical setup. **It is NOT a theoretical ceiling, a guaranteed AP capacity, or an internet download speed benchmark.**

## 3. Explicit Test Limitations & Unvalidated Features

The test results recorded above reflect specific environmental conditions. When interpreting or citing these results, the following limitations must be strictly acknowledged:

1. **Environmental Specificity:** All observations were collected using a specific Raspberry Pi 5, a single mobile phone hotspot (`1+ Four`), and a single Fedora laptop. Performance will vary with radio frequency interference (2.4 GHz spectrum congestion), physical distance, client Wi-Fi chipset capabilities, and cellular signal strength.
2. **Reverse Direction Not Benchmarked:** The reverse TCP throughput test (`iperf3 -R`, Pi transmitting to Client) was not executed. Downlink throughput cannot be assumed identical to uplink throughput.
3. **No Central Access Control Validation:** The policy engine and access control modules (`network/access_control.py`) were not tested end to end. No live MAC filtering, client admission blocking, or quarantine rules were validated in the kernel during this session.
4. **No Bandwidth Shaping Validation:** QoS controls, rate limits, and token bucket filters (`network/bandwidth.py`) were not tested against live traffic streams.
5. **No Integrated Assistant Pipeline Execution:** The end-to-end integration flow (`User Intent -> Assistant Prompt -> MCP Tool Call -> Policy RBAC Check -> Network Mutation -> Verification`) was not validated as a unified operational pipeline. Only the underlying host network infrastructure and individual Python unit tests were verified.
